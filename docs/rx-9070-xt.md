# RX 9070 XT, 32 GB RAM, native 1440p

This preset is for the tested Windows 11 machine with a Ryzen 7 9700X, 32 GB
RAM, and a Radeon RX 9070 XT 16 GB using AMD driver 32.0.32029.2010. It is not a
general performance claim for other GPUs or driver versions.

```powershell
cargo build --locked --profile diag -p victory --features diagnostics
scripts\play.ps1 -Exe <your game_scarlett_master.exe> -Rx9070 -Performance

# Bounded asynchronous experiment; the timeout includes startup and loading.
scripts\play.ps1 -Exe <your game_scarlett_master.exe> -Rx9070 -Performance `
    -Build release -BenchmarkSeconds 300 -Keys '30:Enter,60:Enter' `
    -More @{ VICTORY_LATE_WAIT = '2'; VICTORY_CARD_BUFFERS_MIN_MB = '1' }
```

`-Rx9070` selects the AMD adapter explicitly, renders at 2560×1440 with render
scale 1.0, enables the title's ray-traced indirect lighting, and applies the
memory and compiler workarounds below. Do not add `-Fsr4K` to this preset: that
is a separate 3840×2160-output path.

## Compiler workarounds

The driver crashes in `amdxc64.dll` on several translated shaders. Optimization
mask 59 avoids the startup crashes. The pipeline containing
`CSComputeSkinningTreeAnimVelocity` (shader `f16876929fa64f9f`) crashed under
all 128 tested masks and remains skipped. Its absence can affect animation
velocity and motion vectors; this is a correctness limitation, not a performance
feature.

Upstream `4eb6cfd` also excludes `getDimensions` from the REUSE optimization to
address 29 RDNA4 ray-tracing-resolve compiler crashes. That targeted fix is
included in the integration below, but mask 59 and the skinning-pipeline skip
were retained for its smoke run; the run does not establish that either existing
workaround can be relaxed.

The skip applies in both diagnostics and ordinary release builds. Early pipeline
creation honors it too. Compiler crash records in `warm-bad.txt` are scoped to a
fingerprint of the translation settings and graphics driver. The parser accepts
both the current `<key> fp=<fingerprint>` records and the earlier
`<fingerprint> <key>` records. Untagged legacy and manually added keys remain
applicable, matching upstream's compatibility policy.

## Memory and pacing

Keep a system-managed pagefile. A 32 GB RAM installation can have substantially
more than 32 GB of private commit while physical memory remains below that
amount. The launcher limits idle host-copy retention and stops speculative
texture growth earlier on these machines; required one-shot uploads retain a
smaller emergency floor.

`-Performance` enables renderer ports 1, 2, 5, 6 and 7 and a 33.333 ms frame
interval. The RX preset currently pins synchronous submission explicitly because
its direct RT-arena placement requires that mode. Asynchronous stages 2 and 3
are experimental on this configuration:

```powershell
# Experiment only; the direct in-place RT-arena path falls back to copies.
scripts\play.ps1 -Exe <your game_scarlett_master.exe> -Rx9070 -Performance `
    -More @{ VICTORY_LATE_WAIT = '3' }
```

## Evidence and remaining limits

Native-RT opening tests on this machine have reached 3D with `-Performance`.
Synchronous cell/courtyard samples were about 4 fps. Experimental asynchronous
runs reached roughly 12–19 fps depending on the shot. These are different points
in the opening, not a controlled benchmark, and do **not** establish stable 30
fps. A 30 fps sample containing only 13 draws was a loading screen and is not
world-performance evidence.

The five-second diagnostic samples below summarize the last 40 reports of each
run (about 205 seconds), excluding initial shader compilation and loading. The
card-buffer threshold is the value actually logged at startup, not merely the
value requested by a launcher command:

The last run averaged 48.43 ms preparing, 31.36 ms waiting for the GPU and
23.43 ms copying back. Its scene is not identical to the 1 MiB run, so the
threshold comparison is suggestive, not causal. In particular, an earlier
intended 1 MiB repeat actually logged 4 MiB and must not be reported as that
A/B. `play-20261127-003919-4728.log` includes world/loading transitions and
samples from 0.8 to 29.9 fps with 10 to 5,246 draws; it is evidence that loading
and world samples must be separated, not a stable-world result. No run in this
table meets acceptance, and the loading-only 30 fps result is excluded.

Two unobstructed pairs of window captures were collected. None of those four
frames showed the reported one-frame object enlargement. That is not enough to
prove the artifact fixed or to identify the mandatory shader skip as its cause.
Texture-upload ordering, geometry/skinning, motion vectors and LOD selection
remain separate possibilities.

The generic streamed-texture code defaults to limiting large texture sides to
1024 pixels, with lower limits under VRAM pressure. The current `-Rx9070` preset
sets `VICTORY_TEXTURE_MAX=0`, so new runs keep the largest mips even under
pressure. This is required for acceptance but may increase memory use and frame
time. All measurements in the table above predate that preset change and used
the generic cap; they are diagnostic history, not full-quality acceptance runs.
The launcher records the effective quality and pacing settings at the start of
each new log. A benchmark timeout forcibly stops the test process and returns
exit code -1; that expected timeout is not a title crash.

### Same-scene diagnostic A/B

`play-20261127-065240-20104.log` used the diagnostics build, the complete
renderer-port preset and ten-second phases for spread write-watch asks, fine
heap-sync jobs and joined submission parts. Once the scene became comparable,
phases 16 through 21 averaged 78.4, 79.0, 79.5, 78.2, 78.1 and 77.5 ms with
4,442–4,607 draws/frame. No switch produced a material improvement; all are
about 12.6–12.9 fps. Earlier phases include loading and scene changes and are

`play-20261127-065708-9812.log` similarly alternated write-watch reset policy,
aside guard planning and the sharded port journal. Phases 16 through 22 ranged

### Two-block safe-merge measurement

The landing merge now handles two 32-byte blocks per loop iteration. Both
iterations' title accesses remain inside the registered fault range, so an
unmapped or read-only title page still returns the number of whole blocks left
instead of escaping the safe-copy recovery path. All 12 non-ignored safe-copy
tests passed, including randomized byte/dword merges, concurrent writers and
guard-page failures.

Three alternating runs of saved baseline and candidate diagnostics test
executables used `land::tests::what_landing_costs` (1,536 pieces of 64 KiB).
Median landing times were:

| Case | Baseline | Two blocks |
| --- | ---: | ---: |
| Dense, one thread, direct | 20.7 ms | 20.1 ms |
| Dense, four threads, direct | 10.1 ms | 10.0 ms |
| Dense, four threads, beside | 8.3 ms | 8.2 ms |
| Sparse, one thread, direct | 21.9 ms | 21.0 ms |
| Sparse, four threads, direct | 10.0 ms | 9.6 ms |
| Sparse, four threads, beside | 8.2 ms | 8.1 ms |

This is a small CPU-side improvement, principally on the direct path, not a
whole-frame FPS claim. The bounded release smoke run
`play-20261127-101224-20980.log` used native 2560×1440, render scale 1.0,
uncapped textures, title RT, late wait 3, a 1 MiB card minimum and four landing
threads. It reached 9.4 fps, 106.5 ms/frame and 4,988 draws/frame in its final
heavy sample, with an 814.1 ms world/loading transition. The process was reaped
by the intended 150-second timeout, with no new panic, device removal or
compiler crash. Camera, streaming and draw counts differ from earlier runs, so
this neither establishes an FPS improvement nor satisfies acceptance.

### GPU REUSE screening and card-upload range joining

Full-DRED command timings did not justify changing shader optimization mask 59.
The final mask-63 group in `play-20261127-103911-11188.log` was 47.02 ms against
43.67 ms in the earlier mask-59 run, but the camera and work differed. Within one
run, the same shader's cost varied severalfold. In particular,
`bba90b2f0ff2eada` had a 0.30 ms median in the mask-59 run and 13.70 ms in the
later scene, so the cross-run difference is not a REUSE effect. Normal-runtime
mask 63 was already effectively tied with mask 59. Mask 59 remains selected.
Offline translation of the newly dominant compute shader validated and created
its pipeline at both masks; REUSE reduced its static DXIL instruction count from
7,787 to 6,658, which is not runtime evidence.

Card uploads now join dirty ranges separated by at most 64 bytes. The complete
joined range, including its gaps, is snapshotted and sent; relay bookkeeping uses
that same sent range, so an unchanged gap cannot be mistaken for a shader write.
`VICTORY_CARD_JOIN_GAP=0` restores the old touching-only behavior. This trades at
most 64 bytes of extra upload per removed gap for fewer copy commands; it does
not change texture mips, shader inputs or rendering quality.

Two diagnostics runs alternated the setting every 12 seconds in the same process
(`play-20261127-110831-17228.log` and `play-20261127-111251-6548.log`), using
native 1440p, title RT, uncapped textures, late wait 3, a 1 MiB card minimum and
the fixed opening inputs. Joining reduced the reported upload counts by about
95% (for example, 118,489 to 4,470 and 69,451 to 2,613 ranges per frame in the
two late-world comparisons below).

| Alternating phases (baseline → join) | Draws/frame | Mean frame time | Median | Copy preparation | Upload ranges |
| --- | ---: | ---: | ---: | ---: | ---: |
| First run, phases 12 → 13 | 4,646 → 4,645 | 77.5 → 66.0 ms | 67.9 → 65.3 ms | 21.9 → 17.6 ms | 118,489 → 4,470 |
| Second run, phases 10 → 11 | 4,105 → 3,865 | 60.4 → 57.5 ms | 55.3 → 48.4 ms | 17.1 → 13.6 ms | 69,451 → 2,613 |

Across all seven adjacent world pairs, including transitions and less comparable
draw counts, the median improved in five and the mean in three. These results
support retaining the substantially smaller command stream, not a universal FPS
multiplier. The default-on release smoke `play-20261127-111948-15188.log` ended
with 17.6 and 17.4 fps (56.8 and 57.4 ms), 4,180 and 4,110 draws, and roughly
3,300–3,500 upload ranges. It reported no panic, device removal or compiler
crash and was stopped by the intended 150-second timeout. This remains below the
30 fps acceptance criterion, so no acceptance PR is justified.

### Card-copy preparation follow-up

Diagnostics now separate dirty-range gathering, submission-owned byte snapshots,
and upload-list recording. Heavy samples commonly took 2.5–4.3 ms gathering,
2.4–3.3 ms taking bytes, and 0.5–0.8 ms recording lists per frame. Sorting and
coalescing accounted for nearly all gathering time; list recording is not the
primary cost.

A four-pass 32-bit radix sort did not beat the existing run-aware comparison
sort. In the closest final phases of `play-20261127-124413-17076.log`, radix
recorded 75.5 ms mean and 75.4 ms median against 75.4 and 75.1 ms without it.
An off-by-default per-shadow parallel gather was then tested in
`play-20261127-125715-8076.log`. Its closest late-world phases had 5,013 and
4,982 draws/frame: parallel gathering recorded 67.7 ms mean and 61.7 ms median,
against 60.6 and 58.7 ms serial. Their gathering averages were 4.05 and 3.28 ms,
respectively, so the candidate was removed. Neither experiment changed visual
settings or met acceptance.

### Direct dword change discovery

Ordinary card refreshes previously found exact changed bytes and then widened
each run to the containing dwords. They now call the existing direct dword
encoder, which compares eight dwords per AVX2 vector. Unaligned addresses or
lengths still take the original widening function. The output is therefore the
same, including at partial-page ends; randomized tests now cover every address
alignment and non-multiple-of-four lengths. `VICTORY_SEND_WORD_RUNS=0` retains
the old route for diagnosis.

`play-20261127-133638-19956.log` alternated the routes every 12 seconds. In
stable late-world samples with about 11–12 MiB compared and 110,000–116,000
runs per frame, scalar widening took 11–14 ms across worker threads, while
direct discovery took about 2.4–2.8 ms. The closest completed whole-frame pair
was phase 15 (direct) at 60.8 ms mean, 58.5 ms median and 4,529 draws/frame,
against phase 16 (scalar) at 62.5, 59.9 and 4,485. This is a local fivefold
reduction and a modest whole-frame improvement, not stable 30 fps. A separate
exact-byte AVX2 encoder was not retained after inconclusive whole-frame A/B.
The default-on release smoke `play-20261127-134336-2832.log` completed its
intended 180-second timeout without a new panic or device removal. Its final
heavy sample was 14.4 fps, 69.4 ms/frame and 4,672 draws/frame; acceptance is
still unmet.

### Refresh-journal walk and rejected follow-ups

The write-watch journal now avoids allocating a one-element piece list when a
refresh range lies wholly in one 64 MiB piece. The fast path compares piece
numbers, not shard numbers modulo 64; randomized range tests include a complete
shard cycle, and the four non-ignored port-7 tests pass. The optimized ignored
`one_shard_walk_cost` check measured 45.2 ns for the general walk and 11.2 ns
for the direct one-piece walk. `VICTORY_WATCH_ONE_SHARD=0` retains the old route.

`play-20261127-141949-17448.log` alternated that route every 12 seconds. Later
direct phases generally used less write-watch CPU, but whole-frame results did
not improve: phases 14–17 were 72.2 ms general, 73.1 direct, 70.8 general and
75.6 direct, with 4,847–4,878 draws/frame. This is retained as a smaller local
CPU operation, not an FPS claim. It does not approach the 30 fps criterion.

Two other candidates were not retained. Fusing ordinary card-refresh comparison
and CPU-held updates passed byte/run-equivalence tests, but stable phases 14–17
of `play-20261127-140253-23240.log` alternated 69.7 ms separate, 70.6 fused,
69.5 separate and 69.0 fused. Snapshot costs were 2.93, 2.94, 3.00 and 3.03 ms,
so the fusion was removed. Eight view-worker threads in
`play-20261127-141216-8412.log` did not reduce the heap-slot walk (19.63 ms
against 20.35 ms for the preceding four-worker run) and were not promoted; its
scene-confounded whole-frame result was worse.
